## Overview

Integer identifiers in the public database — `sample_id`, `figure_id`, and `SID` — were not unique, which broke analyses that join the published dataset files on these columns. This release renumbers the affected records, removes empty duplicate paper entries, and adds database-level unique constraints so the problem cannot reoccur.

**The IDs that existed in the public database before the March 2026 migration were not changed.** Only records that arrived with the Closed Databases integrated in v3.0.0, plus a small number of records affected by concurrent registration, received new IDs.

Related issue: [starrydata2#471](https://github.com/starrydata/starrydata2/issues/471)

---

## What Was Wrong

Two independent causes, affecting cleanly separated sets of records:

- **Integration of the Closed Databases (2026-03-31)** — when the four material databases were brought into the public database for v3.0.0, paper identifiers were reassigned, while sample and figure identifiers were carried over from the source databases. Uniqueness was validated within each paper rather than across the whole database, so the resulting collisions were not detected at the time.
- **Concurrent registration** — records created at the same moment could be assigned the same identifier. This accounted for the duplicated paper `SID` values and a small number of sample and figure identifiers.

| Target | Duplicate groups | Excess records |
|---|---|---|
| `sampleid` | 9,728 | 13,331 |
| `figureid` | 4,483 | 5,773 |
| `sid` | 729 | 741 |

---

## What Changed

Applied to production on **2026-09-08**, after rehearsals on a local restore and on staging that produced identical counts.

| Target | Action | Records |
|---|---|---|
| `sampleid` | Renumbered (from the integrated databases) | 13,454 |
| `sampleid` | Renumbered (concurrent registration) | 7 |
| `figureid` | Renumbered (from the integrated databases) | 5,864 |
| `figureid` | Renumbered (concurrent registration) | 1 |
| `sid` | Duplicate papers with no content deleted | 635 |
| `sid` | Duplicate papers with different DOIs renumbered | 106 |

Previous identifiers are preserved on each renumbered record in `legacy_sampleid`, `legacy_figureid`, and `legacy_source`, so old-to-new mapping tables can be produced on request.

Unique indexes are now in place on all three collections.

---

## Impact on Dataset Users

- **Existing IDs from the public database are unchanged.** If your analysis uses `sample_id`, `figure_id`, or `SID` values obtained before this release from the public Starrydata dataset, they still refer to the same records.
- **IDs that arrived with the Closed Databases have changed.** These were published between April 2026 and September 2026.
- **Published datasets have been regenerated.** The snapshot taken on 2026-09-08 verifies clean: 105,999 rows in `starrydata_samples.csv` with 105,999 distinct `sample_id`, 56,489 rows in `starrydata_papers.csv` with 56,489 distinct `SID`, and no `sample_id` or `figure_id` in `starrydata_curves.csv` pointing at more than one paper.
- Google Drive, the [starrydata_datasets](https://github.com/starrydata/starrydata_datasets) repository, and its GitHub Releases have been updated. The Figshare archive picks up the corrected data with its scheduled publication on 2026-10-01.

---

## Verification

All seven checks in the verification script passed on production:

1. Global uniqueness of `sampleid` / `figureid` / `sid`
2. Uniqueness of `(sourceid, integer ID)`
3. Immutability of records that were *not* renumbered
4. Reference resolution (orphan counts unchanged before and after)
5. Legacy fields populated as expected
6. `sourceid` consistency between curves and samples
7. Unique indexes created

Check 3 is the important one for external users: record counts, sums, maxima, and minima over the untouched records matched the pre-work baseline exactly, confirming that no public-database ID was modified.

---

## Reliability

- Unique indexes on `sampleid`, `figureid`, and `sid` are now enforced at the database level, so duplicate identifiers are rejected regardless of application behaviour. They are partial indexes covering positive values, matching how identifiers are assigned during record creation.
- Identifier assignment is being consolidated so that uniqueness is guaranteed at allocation time.
